# VEYRONIX — Failure-Mode Analysis

> Honest catalogue of where VEYRONIX fails and why (spec §52). Generated by `make evaluate`.

## Missed / hard incidents (low root-cause Top-1)

- **model_drift**: Top-1 0% (n=6).
- **traffic_spike**: Top-1 75% (n=4).
- **bad_deployment**: Top-1 100% (n=6).
- **cascading_failure**: Top-1 100% (n=6).

### Why these fail
- **model_drift** has *no infrastructure signature* by design — it shifts an input distribution, so the infra root-cause engine cannot localise it. It is instead surfaced by the drift monitor (§60). This is a deliberate architectural boundary, reported rather than hidden.
- **traffic_spike** is an *external* cause with no precursor: it can be attributed (fleet-wide request-rate rule) but is close to unpredictable for early warning.
- **Deployment coincidence**: a benign deploy near an incident onset can create a competing bad-deploy hypothesis; recency-to-onset weighting mitigates but does not eliminate this.

## False alarms & missed predictions

- At a ≤5% false-alarm budget the active model detects 50% of test incidents; faults with zero precursor (sudden crash / traffic spike) are the main misses.
- Mean warning time is 12.0 min — useful, but short-lead faults compress it toward zero.

## Agent limitations

- Hallucination rate is 0% by construction (claims must be grounded in evidence), but the offline reasoner's *narrative* is templated; a live LLM improves phrasing, not the underlying (deterministic) conclusion.
- Recommendation accuracy is 75%: for incidents with ~zero measured business impact the recommender rationally prefers do-nothing, which differs from the textbook recovery action.

## Environment caveats

- The environment is **SIMULATED**; business-impact figures are model estimates, not financial truth. Real telemetry would introduce noise, missing data and concept drift the current models are not yet tuned for.
